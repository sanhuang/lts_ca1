# 可延後與可重試 — 需求情境說明

> 來源問題：對應 `more.md` §2「把『可延後、可重試、可水平擴展』的工作從即時 WS 熱路徑拆出」。  
> 問題：可延後與可重試的需求情境是什麼？

---

## 一句對照

對照本專案（ROS GNSS → FastAPI → WebSocket 地圖）：

- **可延後** = 地圖先動；DB／雲／重計算可以排後面  
- **可重試** = 排後面的事若碰上暫時故障，要能自動再做，且不因重做弄髒資料  

**可延後**與**可重試**指的是：地圖上的 5Hz 即時點必須立刻推；其餘旁路工作可以晚一點做，失敗了還能再試——不必堵在 WebSocket 熱路徑上。

面試 MVP 兩者都可不做；一旦有持久化 DB、上雲、告警，就會同時需要這兩種特性，也才值得上 Celery + Redis／RabbitMQ。

---

## 可延後（Deferrable）

原則：**不影響「當下位置／軌跡線是否即時出現」**。

| 情境 | 為什麼可延後 |
|------|----------------|
| **寫入 PostgreSQL 軌跡** | 營運回放、事故調查用；晚 0.5–2s 寫入通常可接受，地圖已先靠 WS 更新 |
| **匯總上雲／日報** | 岸端報表本來就不是即時控制迴路 |
| **多載具後處理**（平滑、抽稀、算里程） | 重 CPU，放 Worker 跑，避免拖慢 Bridge |
| **降採樣歸檔**（5Hz 監控、1Hz 落庫） | 可批次或延遲寫，減少 DB 壓力 |
| **非緊急通知**（班次結束摘要、統計信） | 與即時監控無關 |

### 反例（不可當「可延後任務」取代熱路徑）

把座標先丟 Celery，等 Worker 做完再推 WS——地圖會抖、會慢，違反題目即時監控。

---

## 可重試（Retryable）

原則：**失敗多半是暫時性的**（網路、DB 忙、對端維護）；重試後結果應與「一次成功」等價。

| 情境 | 典型失敗 | 為何要重試 |
|------|----------|------------|
| **寫軌跡到 DB** | 連線斷、鎖等待、主備切換瞬間 | 點寫丟了，回放會缺段；重試可補 |
| **呼叫雲端同步 API** | 逾時、5xx、限流 | 白名單 API 偶發不穩，重試比丟資料好 |
| **告警／超速／電子圍籬通知** | 簡訊／Webhook 暫時掛 | 晚到的告警仍有價值（視業務定 SLA） |
| **HA 切換空窗** | Bridge 已 `.delay()`，Worker／DB 尚未就緒 | 任務留在 Broker，起來後繼續消化 |

### 冪等注意

Celery 常是 **at-least-once**（可能重複執行）→ 寫庫要用 `(vehicle_id, timestamp)` 等做**冪等**，避免重試造成重複列。

### 不太適合盲目重試

明確的業務拒絕（400、權限不足）、已確定的重複告警風暴——應進死信／人工，而不是無限 retry。

---

## 與 `more.md` 資料流的對齊

```text
                    ┌─ 熱路徑（不可延後）→ WebSocket 即時座標
/gps/fix → Bridge ─┤
                    └─ 冷／旁路（可延後 + 可重試）→ Celery → Worker
                                              ├─ 寫入 PostgreSQL 軌跡
                                              ├─ 告警／超速判斷
                                              ├─ 匯總上雲
                                              └─ 多載具後處理
```

| 路徑 | 延遲期望 | 失敗策略 |
|------|----------|----------|
| 熱路徑 WS | 毫秒級，跟 5Hz | 斷線重連；不靠 Celery |
| 旁路 Task | 可晚數百毫秒～數分鐘 | Broker 持久化 + retry + 冪等／DLQ |
